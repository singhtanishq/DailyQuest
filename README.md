## What is DailyQuest?

DailyQuest is a growing archive of hand-crafted technical challenges — coding, debugging,
output prediction, SQL, regex, security, networking, Git, Linux, system design and more.
Every date receives exactly one quest. The web app presents today's quest, and lets you
browse, search and filter everything that came before.

There is no AI in the loop and no paid API. The generator is deterministic and
self-verifying: quests whose claims cannot be **executed and confirmed** (reference code,
SQL result sets, regex samples, shell/git sandboxes) are never published.

## Features

- **A quest per day, forever** — generated by GitHub Actions, committed with a real
  artifact (quest + index + statistics), deployed automatically.
- **Deterministic generation** — `SHA-256("DailyQuest:" + date + ":generator-v1")` seeds a
  hash-counter RNG; the same date always produces the same quest.
- **186 curated templates** across 28 categories, with weighted rotation rules that avoid
  repeats and keep difficulty balanced.
- **Machine-verified content** — coding tests run against reference implementations,
  output-prediction snippets execute in a sandbox, SQL is checked against SQLite, regex
  against real `RegExp`, Git/Linux scenarios against throwaway sandboxes.
- **A real product UI** — today's quest, hints that reveal sequentially, gated solutions,
  fuzzy search, shareable filters (`/archive?q=regex&difficulty=hard`), category pages,
  honest publication streaks, dark/light themes, accessible throughout.
- **Zero backend** — the site is fully static; the generated JSON dataset is the data layer.

## How it works

```
GitHub Actions (daily, 00:17 Asia/Kolkata)
        │
        ▼
Date Resolver ──► today in the publication timezone
        │
        ▼
Deterministic Generator
   seed(date) → category → template → difficulty → parameters
        │
        ▼
Verification & Validation
   sandbox execution · schema checks · duplicate detection
        │
        ▼
Quest Archive (data/quests/YYYY/MM/YYYY-MM-DD.json)
        │
        ├──► index.json · stats.json · categories.json · latest.json
        │
        ▼
One commit: feat(daily): publish DailyQuest #NNN — Title
        │
        ▼
Vite build ──► GitHub Pages
```

The daily commit contains the new quest file, the rebuilt derived files, the daily report
and the README status block — nothing else. If the workflow runs twice, the second run is
a no-op (idempotent by design).

## Repository structure

```
├── .github/workflows/     ci.yml · daily-quest.yml · deploy.yml
├── config/                central generator configuration
├── data/                  canonical quest archive + generated JSON
│   ├── quests/2026/10/    one JSON file per published quest
│   └── index.json         compact archive index (search + navigation)
├── docs/                  ARCHITECTURE · GENERATOR · AUTOMATION
├── reports/daily/         one publish report per generated date
├── scripts/
│   ├── daily/             the generator: core, templates, verify, storage, pipeline, cli
│   └── build/             sitemap generation, dist verification
├── shared/                domain types shared by generator and frontend
├── src/                   React frontend (pages, components, data service)
└── tests/                 unit + integration tests (determinism, idempotency, catch-up)
```

**Source vs. generated:** `scripts/`, `src/`, `config/` and `shared/` are human-maintained.
Everything under `data/` (except nothing — it is all generated) and `reports/` is produced
by the pipeline. Quest files are immutable once published; derived files are deterministic
rebuilds.

## Local development

Requires Node 22.12+ (24 LTS recommended).

```bash
npm install
npm run dev          # dev server
npm run build        # validate + typecheck + bundle + sitemap + verify
npm run preview      # serve the production build
```

### Quest pipeline commands

| Command | What it does |
| --- | --- |
| `npm run generate:daily` | Generate today's quest (with catch-up policy) + rebuild derived files |
| `npm run generate:daily -- --dry-run` | Preview today's quest without writing anything |
| `npm run generate:date -- 2026-10-07` | Generate one specific date, if missing |
| `npm run generate:backfill -- 2026-10-01 2026-10-07` | Backfill an inclusive range |
| `npm run validate` | Validate the entire archive; non-zero exit on any error |
| `npm run rebuild` | Rebuild index, stats, categories, latest, health from quest files |
| `npm run quest` | CLI help for all of the above |
| `npm test` | Unit + integration tests |
| `npm run lint` / `npm run typecheck` | ESLint / TypeScript |

### Testing

The suite covers date/timezone resolution, seed derivation, selection + rotation rules,
structural validators, duplicate detection, catch-up planning, and an integration suite
that generates quests into temporary roots and proves byte-identical determinism,
no-op idempotency, and full archive consistency.

## Deployment

The site deploys to **GitHub Pages** with the official Actions toolchain
(`configure-pages` → `upload-pages-artifact` → `deploy-pages`).

- `daily-quest.yml` — schedule + manual dispatch: generate → verify → test → build →
  commit → push → deploy.
- `deploy.yml` — builds and deploys on every non-daily push to `main` (template fixes,
  frontend changes) and can be run manually.
- `ci.yml` — lint, typecheck, tests, data validation and build on every push and PR;
  never commits.

To enable Pages: repository **Settings → Pages → Build and deployment → Source: GitHub
Actions**. The app is served under `/DailyQuest/` (set `DAILYQUEST_BASE_PATH=/` for a user
site or custom domain, and update `robots.txt`/`DAILYQUEST_SITE_URL` accordingly).

## Contribution Attribution Setup

Daily commits are authored and pushed as **you**, not as a bot. GitHub counts a
contribution when the commit's author/committer email belongs to a verified email on your
account and lands on the default branch of a standalone (non-fork) repository. Configure
three repository secrets (**Settings → Secrets and variables → Actions**):

| Secret | Value |
| --- | --- |
| `DAILYQUEST_COMMIT_NAME` | The name you want on daily commits (e.g. your name) |
| `DAILYQUEST_COMMIT_EMAIL` | An email **verified on your GitHub account** (Settings → Emails). Use the `@users.noreply.github.com` address shown there if you keep your email private. |
| `DAILYQUEST_PUSH_TOKEN` | A fine-grained personal access token with **Contents: Read and write** on this repository. Classic PATs work with `repo` scope; prefer fine-grained. |

Checklist:

1. Verify the email you configure belongs to your GitHub account — this is what GitHub
   matches contributions against, not the push credential.
2. Understand the difference: **author/committer identity** (set via git config from the
   secrets above — drives attribution) versus **push authentication** (the token — drives
   permission, and allows the push to trigger the deploy workflow).
3. The workflow verifies the identity before every commit, refuses generic bot emails
   (`github-actions[bot]`, `noreply@github.com`, …), and only ever prints a **masked** email.
4. Daily commits land on the default branch (`main`).
5. The repository must not be a fork for contributions to count.
6. The contribution graph may take some time to update — GitHub does not promise instant
   green squares.

The token never appears in workflow source, logs, or URLs: it is supplied to
`actions/checkout` as its `token` input, which persists the credential in the runner's
git configuration for the duration of the job only.

## Configuration

Central configuration lives in [`config/dailyquest.config.ts`](config/dailyquest.config.ts):
publication timezone, category and difficulty weights, rotation windows, catch-up limits
(`maxCatchupDays: 7`), quality thresholds and the generator version. Environment
overrides (local only): `DAILYQUEST_TIMEZONE`, `DAILYQUEST_BASE_PATH`,
`DAILYQUEST_SITE_URL`. See [`.env.example`](.env.example) — no secrets are ever needed
for local generation.

## Troubleshooting

- **Daily run fails with “Missing repository secrets”** — set the three secrets above.
- **“The configured commit email looks like a bot identity”** — `DAILYQUEST_COMMIT_EMAIL`
  must be your own verified email, not an automation address.
- **Push rejected (non-fast-forward)** — the workflow rebases automatically and never
  force-pushes; if the remote already published the date, it realigns and skips.
- **`Get Pages site failed` at `configure-pages`** — Pages is not enabled with the right
  source. Settings → Pages → Build and deployment → **Source: GitHub Actions**, then re-run
  the deploy workflow. (A failure here never blocks the daily quest commit — Pages
  configuration is only touched inside the deploy job.)
- **The site serves the raw source `index.html`** (e.g. the browser requests
  `/src/main.tsx` and 404s) — a stale *branch-based* deployment of the repository root is
  still live. The first successful Actions deployment of `dist/` replaces it; confirm
  Settings → Pages → Source is **GitHub Actions**, then re-run **Deploy Site**.
- **Pages shows a 404 on deep links** — ensure Pages source is *GitHub Actions* and the
  build ran (the SPA fallback ships as `404.html`).
- **A quest looks wrong** — open an issue with the quest date; published quests are
  immutable and corrected explicitly, never silently rewritten.
- **Missed more than 7 days** — the daily run generates only today and records the gap;
  recover history with `npm run generate:backfill -- <start> <end>`.

## FAQ

**Is the content AI-generated?** No. Every template is hand-written, and every expected
answer is computed by executing real code, SQL, regex or shell/git scenarios at generation
time.

**Can two runs produce different quests for the same date?** No. Generation is a pure
function of the date, the generator version, the configuration and the template pool.

**What happens when the template pool runs dry?** The rotation window re-uses the
least-recently-used templates rather than repeating recent ones; the pool (186 templates
with parameter variation) is designed for years of non-repeating output, and new templates
extend it without touching published quests.

**Does this exist to farm GitHub streaks?** No — the daily commit is the publishing
mechanism of a product that genuinely ships a new artifact every day. The README status
block above is updated by that same pipeline.
